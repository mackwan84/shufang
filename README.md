# 书坊 · shufang

面向中文小说创作的 AI 工作流探索：希望把构思、起草、审读、改稿和故事事实管理串起来，让创作者能够持续参与和掌握作品走向。

> **项目处于早期设计与讨论阶段。** 当前仓库收录设计草案、历史评审材料和辅助文档工作的 ZCode 工作流，尚无可运行的小说创作应用。草案中的技术选型、流程和验收指标仍需验证，不代表已经实现或正式定版。

## 想解决什么问题

AI 辅助写小说时，单次生成一段文字并不难，难的是持续保持人物说话自然、情节有推进、前后事实一致，并让人工修改可靠地影响后续创作。

书坊正在探索以下方向：

- **把规划与落笔分开**：用场景任务向作者模型提供必要信息，减少大纲术语和剧情解释混进人物对白。
- **保留创作者的判断**：在场景确认、候选选稿和改稿环节提供人工参与的位置。
- **让审读与改稿形成闭环**：区分确定性检查与模型审读，修改后的正文重新校验。
- **维护长篇故事事实**：记录人物、事件及其变更，研究如何处理改稿对后文的影响。
- **先验证收益再扩大工程**：比较简单提示、多次采样与复杂工作流的效果，同时核算费用、耗时和人工投入。

目前拟以“都市职场”作为首个验证题材，以番茄小说作为首发对齐平台。具体范围见[设计草案](novel_harness_design.md)，平台要求仍待核查。

## 如何使用这个仓库

目前可阅读和讨论设计，也可在具备相应运行环境时使用已有的文档辅助工作流。

```bash
git clone https://github.com/mackwan84/shufang.git
cd shufang
```

使用支持 Markdown 的编辑器打开文档即可。设计草案包含 Mermaid 图，支持 Mermaid 的预览器可以显示流程图。

**应用安装、启动和测试命令暂未提供。** 当前没有 `package.json`、应用入口或自动化测试套件；`.dwf.ts` 文件依赖 ZCode 工作流运行环境，不能作为普通 Node.js 脚本直接运行。

草案提及的 `@earendil-works/pi-durable`、`@earendil-works/pi-ai`、SQLite，以及 `packages/core`、`packages/web`、`packages/bench` 等目录均属于拟议方案。依赖可用性、版本兼容性和底座能力仍须通过技术探针确认，仓库尚未安装这些依赖或建立这些应用包。

## 后续如何推进

以下是草案中的阶段设想，不代表已启动或已通过验收：

| 阶段 | 计划验证的内容 |
| --- | --- |
| S0：摸底探针 | 模型写作效果、工作流增益、底座可行性，以及成本和耗时 |
| S1：单题材原型 | 都市职场题材下的起草、选稿、修补与事实管理闭环 |
| S2：盲测验收 | 与单提示直出、等预算多次采样分别比较，评估质量和人工投入 |
| S3：长程验证 | 长篇一致性、存量手稿建档及更完整的本地创作流程 |
| S4：后续探索 | 专家包生态与桌面应用；以此前验证结果为前提 |

近期按以下顺序推进，具体背景与约束见[草案第 7、8 节和附录 A](novel_harness_design.md)：

1. **平台条款核查（创作者）**：查阅番茄小说现行作家专区公告与签约合同范本，核实 AI 辅助创作申报、全勤奖资格及版权归属；以来源、核查日期、结论和未确认项完整记录到草案第 6.4 节为完成标准。
2. **S0 预登记与资产冻结（S0 实验执行者）**：跑数前冻结场景卡集、α 消耗函数和统计分析代码版本；完成标准是三者的版本或提交号均可定位，并记录在当轮实验材料中。
3. **S1 人工预算确认（创作者，S1 启动前）**：明确每千字成稿可接受的人工干预分钟数上限，并据此确定影子期 `routine` 场景抽样比例；未确认前不启动 S1。

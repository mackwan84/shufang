### 1.2 核心共识：定位修正推翻了原方案的“承重墙”

六位评审在第一轮独立审查中全部达成同一核心判断：原方案的架构骨架是围绕“成人内容被闭源模型拒写”（`novel_harness_design.md:19, 35`）这一单一前提搭建的。当用户将主体定位修正为“面向广大读者、可公开发布的各类题材中文小说”后，原方案由此推导出的五项核心设计——**D1 成人内容硬约束（`:35`）、正文层只用开源模型（`:83, :94`）、资料员兼任脱敏边界（`:70, :90`）、主编只读结构化状态不读正文（`:37, :64`）、“语料和正文都不出本机”的无条件承诺（`:151`）**——其推理前提已不成立。

对主体场景而言，原方案同时存在两方面失衡：
1. **过度设计**：用个人支线题材的防审查需求约束全局，将闭源 API 模型一刀切挡在正文层外（且与 D13 `:47` 配置化原则自相矛盾），并在无需脱敏的常规创作中引入资料员单通道有损压缩。
2. **设计不足**：全文未定义任何角色失败/超时/拒答语义（`grep` 0 命中）、三种长程状态缺乏唯一事实源与版本链、A/B 盲读验收缺乏统计与基线定义、面向公开发布缺少 AIGC 标识与版权查重机制、缺少单场调用与人工时间预算。

### 1.3 主要交锋点与裁决走向

在交叉互评与终审复核中，评审团围绕八个核心分歧展开了激烈辩论：

1. **内容策略路由粒度與模型预设：按“场景”切模型 vs 按“作品”锁模型，闭源是否天然更强？**
   - *交锋*：架构评审建议按场景打 `general / mature / explicit` 标签动态路由模型；产品运营与魔鬼代言人强烈反对，指出书内逐场切换作者模型会导致文风与人物声线断崖式割裂，且前场正文进入下场上下文仍会触发云端拒答。同时，产品运营声称“主流题材占 80% 以上、闭源旗舰完全无拒答且文笔普遍高于开源”，遭到架构、网文、模型技术、合规、魔鬼五方一致反驳（无数据支撑，悬疑/历史等题材同样存在暴力弱化与道德说教等“软拒答”，且 DeepSeek-V3 等属开放权重模型）。
   - *裁决*：采用**作品级 Profile + 四轴正交配置**（内容尺度、数据驻留、端点政策、模型能力），作品内固定作者模型，个别尺度冲突场次走人工接管或侧面改写；否决“闭源普遍更强/完全无拒答”的先验断言，留待 S0 实测，并将“拒答/软拒答”列为独立失败类型。
2. **主编能否读正文与脱敏触发条件：按“题材公开与否”还是按“数据外发白名单”？**
   - *交锋*：第一轮多数评审赞成“公开题材下允许主编读最小必要正文，private 模式下维持脱敏”。但独立终审敏锐指出这与“四轴正交”和“公开出版意图 ≠ 概括同意将未发表手稿外发”自相矛盾（例如：公开题材但设为 `strict_local` 的作品配云端主编该不该读正文？`private` 作品配纯本地主编为何还要脱敏？）。
   - *裁决*：终审意见成立。**主编（及任何角色）能否读未发表正文，只由“该角色所绑端点是否在该类数据的外发白名单内”决定，与题材是否公开完全解耦**；脱敏仅在“数据要离开其允许可见域”时启用；新建作品默认关闭所有正文/范文/摘要外发，首次配置云端端点时逐类显式授权。
3. **资料员单点故障与状态回滚：叠加复核 Agent + 全量级联重算 vs 单次带证据抽取 + 局部 Diff 待复核**
   - *交锋*：架构评审主张新增摘要 Agent、用另一模型逐场复核、章节节点强制人审圣经 Diff，并在修改第 $k$ 场时级联失效重算第 $k+1 \dots n$ 场的所有状态与摘要。产品运营、网文编辑、模型技术、合规风险、魔鬼代言人一致反驳：每场加 2 个 Agent 和强制审 Diff 会让成本与人工负担爆炸；LLM 抽取非确定性会导致级联重抽覆盖作者后续手动修正的设定。终审进一步指出：仅规定派生态（摘要/索引）惰性重算还不够，事实层修改如何向下游传播、以及资料员看不见主编私有层如何区分“角色撒谎”与“客观事实”均悬空。
   - *裁决*：不新增 Agent；资料员单次结构化输出返回 `delta + 原文证据引用`，由确定性代码校验 Schema、实体与时间线；**代码以只读方式向资料员提供本场定性所需的最小私有层信息（禁透清单、验收项）以区分谎言与事实**；修改第 $k$ 场时只重抽第 $k$ 场并与原 delta 做 diff，下游受影响条目按实体/字段依赖标记“待复核”进入冲突队列，派生态打 `stale` 标记惰性重算。
4. **场景卡防泄漏与字段预算：十余字段双层卡 vs 完全隐藏结局 vs 6 创作字段 + Closing Image**
   - *交锋*：魔鬼代言人指出 `关系变化`（`:107`）是结局节拍，告诉作者模型会导致角色在场末把关系升华念出口，主张完全移入不可言说且不给作者；网文编辑与架构评审反驳：若完全隐藏，作者模型不知本场目标，无法保证关系变化发生，网文编辑进而提议包含十余个字段的双层卡片；产品运营反驳十余个必填项填表超 800 字、导致清单式机械表演，主张将抽象关系变化转化为具体的`收尾画面锚点（Closing Image）`。终审指出新增 `pov_character`、`timeline_mode` 等字段后与“约 6 个核心字段”预算对不上。
   - *裁决*：拆为主编私有层与作者可见层；**元数据字段（POV、时间模式、时间锚点、tier、分支）与创作字段分开计数**；作者可见创作字段控制在 6 个（人物欲望、顾忌、信息差、潜台词、说话习惯、收尾画面锚点 Closing Image），“不可言说”转化为可表演外部动作/回避行为注记，抽象关系术语留私有层供审读与资料员验收。
5. **质量闭环、影子审读与单稿快速通道的内部冲突**
   - *交锋*：为解决“低分无生产者”（`:39, :131`）与“未校准裁判只送低分稿给人看”的循环偏差，五方共识在 MVP 采用“人工选稿 + 审读影子模式”，产品运营提议 `routine` 日常场单稿快速通道、魔鬼代言人提议人工 UI“只看裁判前 2 名 + 差异摘要”以控人工耗时。但独立终审查出三处致命冲突：① 影子期若只给人看“裁判前 2 名”，人选范围已被裁判过滤，一致率天然虚高、偏好库被污染；② `routine` 默认单稿与 D6“淘汰后不足 2 版进人工”字面冲突（导致单稿 100% 进人工）；③ D5 将“审读位置交换结论不稳定”作为闸门信号，却又规定“生产侧只随机顺序、不做交换”。
   - *裁决*：终审三项指正全部采纳。**影子期必须向人展示全部候选（随机顺序、隐藏裁判结论）**，“前 2 名 + 差异摘要”仅在审读达标放权后启用；`routine` 在影子期按比例抽样生成多稿；失败矩阵按 `tier` 分道（`routine` 单稿为校对+任务验收过即放行，不过则补生成 1 版再走人工）；多稿场景生产侧**固定做 2 次正逆序 Listwise 审读**，天然产出位置交换稳定性信号。
6. **S0 轻量探针与“先验证再写框架”闸门的统计效力悖论**
   - *交锋*：魔鬼代言人提出在 S0 做同模型四条件消融以检验 Harness 是否有增量；产品运营反对模型技术评审将 S0 扩为耗时数周的多维方差实验，主张维持 1~2 周、约 10 张卡的轻量探针；模型技术指出样本量小时“区间过宽 = 证据不足而非证伪”。独立终审一针见血地指出：按二项检验（5/5 全胜双侧 $p=0.0625$），10 张卡几乎不可能得出统计显著的结论，若“证据不足”不绑定具体动作而默认进入 S1，则 `:29`“先验证、再写框架”的闸门形同虚设；且第一轮裁决把七八项消融全塞进 S0 根本做不完。
   - *裁决*：**S0 必须预先登记“继续 / 扩样 / 转向”决策表**（点估计低于阈值则不建完整 Harness；点估计达标但区间过宽则必须执行扩样至指定卡数与预算上限，禁止默认继续）；S0 只保留 4 项 P0 任务（四条件消融+决策表、底座 Spike、成本时延基线、软拒答发生率抽测），其余 5 项消融全部降为 P1 移入 S1 开发集。
7. **兜底检索方案与中文分词缺陷**
   - *交锋*：架构与魔鬼核实 `pi-ai` 无内置 Embedding，产品建议砍掉向量索引改用 SQLite FTS5。独立终审指出 SQLite FTS5 默认 `unicode61` 不切中文，`trigram` 分词器对少于 3 个字符的子串无匹配，搜不到两字中文人名（如原文 `:18` 的“薇薇”）。主持人在 `sqlite3 3.54.0` 现场实测证实了该缺陷。
   - *裁决*：MVP 兜底检索改为 **SQLite FTS5 + 两字专名走实体表直查 / `LIKE` 补充**（或 `jieba` 分词扩展），并将中文检索验证列入 S0 底座 Spike。
8. **开发工作量切分与衍生功能边界**
   - *交锋*：产品运营提议增加 Showcase 传播卡片导出、导入连载平台读者评论反哺故事圣经、在 S1 落双题材专家包并用外部编辑器直改 Markdown 文件。网文、魔鬼、模型、合规、架构分别从泄漏未公开设定/范文、评论污染正史与个保法风险、违反 `pi-durable` 单进程独占存储、范围膨胀等角度予以反驳。同时，独立终审警告：若把本场评审新增的所有机制（分支、已发布状态、脱敏过滤器、完整偏好库等）全部定为 S1 动工前必做，会导致 MVP 无法启动，且让已降级的 `private` 机制重新主导工程。
   - *裁决*：否决 Showcase 传播包、评论反哺圣经、商业化接口与外部编辑器直改文件；**将所有修订项严格切分为“MVP 必做 / 结构预留（仅 Schema）/ 后续阶段”三档**，确保单题材 MVP 轻量聚焦。

## 四、仍存疑、留给方案作者决定的事项

以下事项涉及作者个人创作目标、资源预算或外部商业环境，评审团已完成利弊分析与候选方案收敛，需由方案作者在动工前拍板：

1. **【P0 阻塞项】S0 与 S1 MVP 的单一主打公开题材与目标读者定位（裁决 V32）**
   - **背景**：定位修正后，S0 的约 10 张摸底场景卡、S1 的 3~5 万字中篇 MVP、内置的首个示例专家包及 S2 盲读读者招募，均以锁定一个具体的主打题材为前提。
   - **已定约束**：① 必须是可全网公开展示的主流可发布题材（官方仓库严禁出现 NSFW 内容）；② MVP 严格锁定 **1 个题材**（不扩为 3 个题材）。
   - **待作者决定**：从候选方向（如**悬疑推理、都市职场/言情、古风权谋、科幻/奇幻**）中选定 1 个作为 MVP 题材，并明确其目标发布平台类型（如起点/番茄/晋江/知乎盐选/豆瓣阅读），以便对齐篇幅节奏与导出格式。
2. **【P0 阻塞项】S0 预登记决策表的具体数值阈值与扩样预算上限（裁决 V19、D10）**
   - **背景**：为防止 S0 轻量探针（约 10 张卡）因统计检验功效不足而沦为“无论结果如何都默认进入 S1”的形式主义，裁决要求在跑 S0 之前预先登记决策表。
   - **待作者决定**：
     - **停工/转向阈值**：在 S0 配对盲评中，“完整闭环（条件 iv）”相对“同模型大纲直出（条件 i）”的胜率点估计低于多少（例如 $< 55\%$ 或 $\le 50\%$），且无明显防泄漏优势时，直接判定不建重型 Harness、改做轻量辅助工具？
     - **扩样预算上限**：若点估计达标（如 $\ge 65\%$）但因样本小置信区间过宽（证据不足），作者愿意追加多少张场景卡（如扩至 20~30 张）及多少 API 预算完成复测？
3. **【P1 体验与成本权衡】S1 人工时间预算上限与「场景卡轻量确认站」的默认开关（裁决 V19、V31）**
   - **背景**：MVP 阶段采用“人工选稿 + 影子审读”，且增加了章节成稿关卡。
   - **待作者决定**：
     - 作者本人可接受的**「每千字成稿的人工干预分钟数」上限**是多少？（此数字直接决定影子期 `routine` 场景抽样出多稿的比例）。
     - 主编生成场景卡后的**「场景卡轻量确认站（Card Checkpoint）」**在 MVP 中默认设为**“每场必停等作者扫视 10 秒确认”**（防方向跑偏白烧 10 次调用），还是**“仅 `climax` 关键场暂停、`routine` 场自动流转”**？
4. **【P1 路线图排期】「存量手稿逆向建档导入（Brownfield Ingestion）」是否提前至 S1 MVP？（裁决 V28）**
   - **背景**：产品运营指出“作者已有数万字半截旧稿希望导入续写、并直接将本人旧稿切片作为零版权风险专属范文库”是极高频刚需；主持人将其定为高优先设计项，默认排在第二阶段（S3）。
   - **待作者决定**：作者在 S1 试写 3~5 万字中篇时，是打算**从第 1 章全新开坑（Greenfield，则维持在 S3 实现）**，还是**用自己手头已有的半截旧稿做测试（Brownfield，则需将该逆向建档脚本提前至 S1 实现）**？
5. **【P2 验收资源】S2 里程碑验收的外部盲读读者招募方式與样本规模（裁决 V18）**
   - **背景**：S2 验收要求包含非作者本人的目标题材盲读者（至少 3 名以上），并采用分块派发防止单人阅读疲劳。
